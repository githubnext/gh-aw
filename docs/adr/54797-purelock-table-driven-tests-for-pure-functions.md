# ADR-54797: Adopt PureLock Table-Driven Testing Strategy for Pure Functions

**Date**: 2026-08-22
**Status**: Draft
**Deciders**: pelikhan, PureLock automation

---

### Context

Several pure Go functions in `pkg/linters` and `pkg/workflow` had zero or low unit test coverage. For example, `parseClaudeJSONArrayBuffer` and `parseEventTypes` had 0% function coverage, and `hasOpenShellArithmeticExpression` had 66.7% coverage. These functions are deterministic with no side effects, making them ideal candidates for exhaustive unit testing. Untested pure functions create silent regression risk when refactored or extended.

The PureLock system was introduced to rank pure functions by a coverage-weighted, type-checked, side-effect-analyzed score and automatically generate test suites for the highest-priority candidates.

### Decision

We will use **table-driven unit tests** (Go's idiomatic `t.Run` subtests over a `[]struct` test table) as the standard format for locking down pure functions identified by PureLock. Each targeted function receives 100% branch coverage via exhaustive boundary cases enumerated in the table. Fuzzing is not used for functions whose input space is small and fully enumerable.

### Alternatives Considered

#### Alternative 1: Fuzz Testing

Randomized fuzz inputs could discover unexpected edge cases beyond manual enumeration. Considered for `hasOpenShellArithmeticExpression` (a byte-scanner with complex quote/paren state). Rejected because the table-driven approach already achieved 100% branch coverage by explicitly enumerating all boundary conditions (quote toggling, nesting, escape sequences, word boundaries). Fuzz testing would add setup overhead and CI instability without improving the coverage achieved.

#### Alternative 2: Property-Based / Quickcheck-Style Testing

Property-based testing (e.g., `gopter` or `rapid`) would auto-generate inputs from invariant definitions. Considered as a more principled alternative for `parseEventTypes` (a type-switch). Rejected because the type-switch has a small, fully enumerable set of branches that table-driven cases cover completely, and introducing a new testing framework dependency is not warranted for functions of this complexity.

### Consequences

#### Positive
- All three targeted functions reach 100% function coverage; overall package coverage improves measurably.
- Table-driven tests serve as executable documentation: each row names and demonstrates a concrete contract of the function.
- The approach is idiomatic Go, requiring no new dependencies or tooling.

#### Negative
- Tests are static tables: if a targeted function's behavior expands (new branch added), the tables must be manually extended — there is no automatic safety net.
- Pure test-only PRs generated by PureLock add code volume (166 lines here) without changing production behavior, which may inflate business-logic line counts for ADR thresholds.

#### Neutral
- Pre-existing test failures in `pkg/workflow` (`TestMaskOTLPHeadersScript`, `TestMaskOTLPAttributesScript`) are environmental/node-runtime related and are not introduced or affected by this change.
- The PureLock system runs as an automated workflow; human review of generated test cases is still required before merging.

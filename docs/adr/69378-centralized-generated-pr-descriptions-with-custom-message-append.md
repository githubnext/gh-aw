# ADR-69378: Centralized Generated PR Descriptions with an Append-Only `--pr-message`

**Date**: 2026-02-25
**Status**: Draft
**Deciders**: pelikhan

---

### Context

Seven `gh aw` commands create pull requests on the user's behalf (`init`, `add`, `add-wizard`, `update`, `upgrade`, `deploy`, and `pr transfer`). Each built its PR body inline at the call site, producing short, generic text such as `"This PR updates agentic workflows from their source repositories."` that told reviewers nothing about which pins moved, which files changed, or which codemods were applied. There was also no way for a caller to attach their own context (a tracking issue, a rollout note) to the generated PR, and no attribution identifying which CLI version produced the change. Because `update --org` and `deploy` can touch many workflows at once, any richer description also has to stay inside GitHub's 65,536-character body limit — and must fail *before* the CLI commits, pushes a branch, or closes an existing stale PR, so a rejected description never leaves the repository in a half-mutated state.

### Decision

We will centralize pull request description construction in a new shared module, `pkg/cli/pr_description.go`, and have every PR-creating command build its body through it. The module provides four primitives: `addPRMessageFlag` (registers the common `--pr-message` flag), `appendPRMessage` (append-only composition of user text onto the generated body), `withPRFooter` (a single `Generated by gh aw v...` attribution line applied once at `gh pr create` time), and `validatePRBody` (rune-count validation against `maxPRBodyCharacters`, footer included). `--pr-message` is deliberately *append-only*: it never replaces the generated summary, so machine-generated change detail is always preserved. Validation is invoked at the entry of each PR-creating path (`createPRWithChanges`, `createPRForRepo`, `addWorkflowsWithPR`, `createTransferPRWithAutoMerge`, and the org/target-repo update path) so oversized bodies are rejected before any commit, push, or stale-PR close occurs. Per-command summary generation (pin transitions, compiler changes, codemods actually applied, capped file lists) lives in `pkg/cli/update_pr_summary.go` and feeds the shared composition helpers.

### Alternatives Considered

#### Alternative 1: Keep per-command inline body construction and add `--pr-message` to each site

Each command already owned its body string, so the smallest change would have been to append the user's message locally in all seven places. This was rejected because the cross-cutting invariants — exactly one version footer, body-size validation before side effects, and consistent Markdown structure — would have had to be re-implemented and re-tested seven times, and divergence between commands is exactly the problem the PR set out to fix. A single module makes "validated once, footer once" a property of the type, not of reviewer discipline.

#### Alternative 2: Make `--pr-message` replace the generated description

A replace-semantics flag is simpler to explain and gives the caller full control of the body. It was rejected because the primary value of this change is the generated change summary (pin transitions, release links, applied codemods); allowing it to be silently discarded would reintroduce opaque maintenance PRs for exactly the users who care enough to pass a message. Append-only keeps the audit trail intact while still letting callers add context.

#### Alternative 3: Truncate oversized descriptions instead of rejecting them

Rather than erroring at 65,536 characters, the CLI could trim the body and append an ellipsis. This was rejected because silent truncation would drop the most important content — the tail-end pin details and the version footer — without the user noticing, and for `update --org` it could produce a PR that *looks* complete but omits changes. Instead the body is bounded proactively (grouped compiler/codemod results, a 50-path display cap that retains the full pin list) and a still-oversized body is a hard error with actionable guidance.

### Consequences

#### Positive
- Reviewers of CLI-generated PRs see what actually changed — pin transitions, release links, affected files, and the codemods that were really applied rather than merely available.
- Every PR carries `Generated by gh aw v...`, making it possible to attribute a bad generated change to a specific CLI version.
- `--pr-message` is registered and parsed identically across all seven commands and both `--repo` and `--org` modes, so there is one behaviour to document and test.
- Oversized descriptions fail before commit, push, or stale-PR closure, so a rejected run never leaves a dangling branch or a closed PR with no replacement.

#### Negative
- All PR-creating commands now share a single module, so a regression in `pr_description.go` affects every command at once; the blast radius of a bug there is wider than the previous per-command code.
- `validatePRBody` is called at several independent entry points rather than at one choke point, so a future PR-creating path can be added without validation unless the author remembers to wire it in.
- Richer summaries make bodies substantially larger, which brings routine `update --org` runs measurably closer to the GitHub body limit than before; the 50-path cap and result grouping are mitigations, not guarantees.

#### Neutral
- `runFixCommand` gained an `OnApplied` callback (via `runFixCommandWithResults`) purely so that upgrade can report codemods that were actually written; the existing non-reporting call path is preserved by passing `nil`.
- `PRInfo.PRMessage` is marked `json:"-"`, carrying caller input through an otherwise API-shaped struct rather than as a separate parameter.
- Codemods are included in PR summaries only after the workflow update and any required Serena scaffolding both succeed; partial failures retain their error reporting without claiming a completed migration.
- The ADR/file numbering uses the PR number (`69378`), matching the existing convention in `docs/adr/`.

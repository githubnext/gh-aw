# ADR-47991: Extend `engine.driver` to Accept Inline Source Objects

**Date**: 2026-07-25
**Status**: Draft
**Deciders**: Unknown

---

### Context

Copilot SDK workflows in gh-aw require a custom driver script that implements the Copilot SDK contract. Until now, the `engine.driver` field only accepted a workspace-relative file path or a bare command name, meaning users had to commit a separate driver file (`.py`, `.js`, `.cjs`, etc.) to their repository before the workflow could run. This extra file creates friction for onboarding, for AI-generated workflows, and for simple use-cases where the driver is a few lines. The compiler already supports multiple Copilot SDK runtimes (Node.js, Python, Go, Java) and can materialize runtime files from config, so the capability to write files before execution already exists.

### Decision

We will extend the `engine.driver` field to accept either the existing string form (path or bare command) **or** an inline object with exactly one runtime key (`node`, `python`, `go`, or `java`). The compiler will validate the inline form (rejecting both empty objects and multi-key objects), materialize the source to a generated file under `${GITHUB_WORKSPACE}/.gh-aw/copilot-sdk/` at runtime, and point driver execution at the generated wrapper rather than requiring a checked-in file. Inline drivers are restricted to the Copilot engine only; other engines continue to require the string path form.

### Alternatives Considered

#### Alternative 1: Keep requiring committed driver files (status quo)

Users continue to commit a separate `.py`, `.js`, or other driver file to their repository and reference it with a string path in `engine.driver`. This is simple to implement (no change) and keeps driver code reviewable as a first-class repository file. However, it adds friction for short drivers, prevents fully self-contained AI-generated workflows, and requires repository write access just to configure a Copilot engine. It was rejected because the overhead is disproportionate for simple drivers and blocks important use-cases like inline AI-authored workflows.

#### Alternative 2: Support a URL or content-addressable reference to an external script

Allow `engine.driver` to reference a URL (e.g., a GitHub raw file URL or gist) and fetch the driver at runtime. This keeps the workflow frontmatter small and allows driver reuse across repos without committing. However, it introduces a network dependency at runner startup, complicates caching and security review, and requires credential handling for private sources. Inline source was preferred because it keeps the full driver intent visible in the workflow file itself and avoids network risk.

### Consequences

#### Positive
- Copilot SDK workflows can be fully self-contained in a single YAML file, eliminating the need to commit a separate driver file.
- Simpler onboarding path: authors can prototype and iterate on driver logic directly in frontmatter without repository file management.
- AI-generated workflows (including those generated by gh-aw itself) can embed complete driver implementations inline, enabling end-to-end automation.
- Schema validation enforces the one-runtime-key constraint at parse time, catching authoring errors early.

#### Negative
- Inline source code embedded in YAML is harder to read, syntax-highlight, and review for drivers beyond a few dozen lines; encourages keeping drivers small.
- Runtime file materialization adds a code path in the compiler that must be maintained across supported runtimes (Node, Python, Go, Java), increasing surface area for future regressions.
- Generated driver files under `.gh-aw/copilot-sdk/` are workspace artifacts; workflows that inspect workspace state may need to account for these transient files.

#### Neutral
- The inline form is Copilot-engine-only; the restriction is enforced by the compiler but not by the JSON schema itself, so misuse on other engines will surface as a runtime error rather than a schema error.
- Existing string-form `engine.driver` usage is fully preserved; no migration is required for current users.
- SDK/toolchain installation (npm, pip, go get, Maven) is triggered by the inline runtime key, matching the same detection path as the explicit `copilot-sdk: true` flag.

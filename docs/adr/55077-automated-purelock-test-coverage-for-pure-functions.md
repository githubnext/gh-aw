# ADR-55077: Automated PureLock Test Coverage for Pure Functions

**Date**: 2026-08-23
**Status**: Draft
**Deciders**: github-actions (PureLock automation), pelikhan

---

### Context

The codebase contains a number of Go functions that have been statically confirmed to be pure (no I/O, no global mutation, no argument mutation). Several of these functions had very low unit test coverage: `validateGitHubAppJSON` at 16.7%, `hasNodeRuntimeRunInstallScripts` at 17.6%, and `extractAmbientContextMetrics` at 54.2%. Low coverage on pure functions is a reliability risk because regressions in their output — which is entirely determined by inputs — would go undetected. The PureLock automation pipeline ranks pure functions by coverage weakness and generates high-coverage table-driven test suites for them automatically.

### Decision

We will use the PureLock automation to systematically identify pure Go functions with low coverage, generate exhaustive table-driven test suites for them, and commit those suites to the repository via automated PRs. This PR applies that approach to `validateGitHubAppJSON`, `hasNodeRuntimeRunInstallScripts`, and `extractAmbientContextMetrics`, bringing each to 87.5%–100% function coverage.

### Alternatives Considered

#### Alternative 1: Ad-hoc Manual Test Authoring

Developers add tests organically when working in a package or when a regression is discovered. This requires no tooling investment and keeps tests close to the development context that motivated them.

Not chosen because low-coverage pure functions are easy to overlook under organic workflows, and the static purity guarantee means automation can safely generate correct, exhaustive cases without the risk of side-effect surprises.

#### Alternative 2: Property-Based Fuzzing with `go test -fuzz`

Use Go's built-in fuzzer to generate random inputs for pure functions and detect panics or invariant violations automatically, without hand-coding expected outputs.

Not chosen for this set of functions because the PR body notes that the input space is already well-characterized by the table-driven cases (all branches covered), and the functions operate on structured inputs (JSON strings, nested maps) where schema-aware table cases provide more readable, reviewable coverage than fuzzer-generated bytes. Fuzzing remains a future option for functions flagged `fuzz_friendly: true`.

### Consequences

#### Positive
- Function coverage increases dramatically: 16.7% → 100% (`validateGitHubAppJSON`), 17.6% → 100% (`hasNodeRuntimeRunInstallScripts`), 54.2% → 87.5% (`extractAmbientContextMetrics`).
- Pure functions are regression-locked: any change to their output behavior will immediately break the table-driven assertions.
- Automation removes a recurring manual effort: coverage gaps in pure functions are detected and patched without requiring developer attention.

#### Negative
- Bot-generated tests require human review before they are considered authoritative documentation of intended behavior.
- Table-driven cases document the current behavior as truth; if the intended behavior changes, both the implementation and the generated tests must be updated together — there is no independent oracle.

#### Neutral
- The `pkg/parser` and `pkg/cli` package-level coverage increases are modest (72.6% → 73.0% and 63.607% → 63.625% respectively) because the new tests cover only three functions within larger packages.
- Residual uncovered branches in `extractAmbientContextMetrics` (internal comparator branches in the stable-sort closure) are structurally unreachable with the concise table needed; they do not affect the primary paths.
